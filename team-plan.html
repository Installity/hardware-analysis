§2What the starter code gives us

About 400 lines of plain Java, all static methods, no libraries. It was compiled and demo was run on Fionn's laptop (Intel Core Ultra 7 258V, 8 cores, 31 GiB, 27 PCI and 6 USB devices) with OpenJDK 27. It works. Each class is short enough for everyone to read in one sitting, and the brief warns that we will be asked how they work.

ClassWhat it doesThings we must understand or fix
sysFileReads a file as text, lines or a number. Returns "" / -1 instead of throwing. Honours -Dhw.root= for testing against a copied folder.This is why missing files never crash the program. hw.root is our best testing tool (see §9).
cpuInfoCounts processor lines, finds model name, sums tick columns from /proc/stat. getCount() counts logical CPUs, not physical cores; with hyper-threading they differ.
Busy = user+nice+system+irq+softirq+steal. Idle = idle+iowait. Guest columns are skipped because they are already counted inside user.

Two findings from the test machine worth using in the interview. First, the 258V is a hybrid CPU. CPUs 0–3 are P-cores (48K L1d, 2.5 MB L2, 12 MB L3), and CPUs 4–7 are E-cores (32K L1d, 4 MB L2 shared by all four, and no L3 listed). /sys/devices/cpu_core/cpus and /sys/devices/cpu_atom/cpus say which is which. Second, there is no hyper-threading, so logical = physical = 8 here. That is not true on most desktops, so check it on each machine.

The pieces everyone should be able to write on a whiteboard

CPU load from two readings. /proc/stat counters only go up, counting ticks (normally 100 per second, USER_HZ) since boot. The load over the last second is the share of new ticks that were busy:

long[][] a = CpuSampler.snapshot();      // a[core] = {busy, idle}
Thread.sleep(1000);
long[][] b = CpuSampler.snapshot();
for (int c = 0; c < cores; c++) {
    long dBusy = b[c][0] - a[c][0];
    long dIdle = b[c][1] - a[c][1];
    long dTotal = dBusy + dIdle;
    double pct = dTotal == 0 ? 0.0 : 100.0 * dBusy / dTotal;   // guard: no ticks → 0%
}

Sorting two ways. PciDevice implements Comparable<PciDevice> gives the natural bus→device→function order. A Comparator gives vendor-name order, using address as the tie-break. Sort copies of the list so the original order is kept.

List<PciDevice> byAddr = new ArrayList<>(devices);
Collections.sort(byAddr);                                   // uses compareTo (bus, dev, fn)

List<PciDevice> byVendor = new ArrayList<>(devices);
byVendor.sort(Comparator.comparing(PciDevice::getVendorName, String.CASE_INSENSITIVE_ORDER)
                        .thenComparing(Comparator.naturalOrder()));

Summary. A TreeMap<String,Integer> counting devices per vendor and per base class, e.g. Bridge 6, Serial bus controller 8. We also print a few derived sentences. The brief says this is the kind of output it wants.

§6Extensions

The brief needs at least one. We do one in depth, one lighter one that reuses core code, and a cheap presentation add-on. Anything marked stretch gets cut first if we fall behind.

Extension 1: Memory hierarchy explorer primary · , buddy

This is the most Computer Organisation of the options: it measures caches from inside Java and then checks the measurements against what the OS reports.

  1. Cache line size: stride test. Allocate an int[] much larger than L3 (64 MiB). Touch every s-th element for s = 1, 2, 4 … 256, and time per access. Cost rises until the stride reaches one cache line (16 ints = 64 B), because from then on every access is a fresh line. After that it flattens. Expect the hardware prefetcher to blur this, and be ready to say so.
  2. Cache sizes: pointer chase. For working sets from 4 KiB to 256 MiB, build a random single cycle in an int[] (Sattolo's shuffle) and follow it. Each load depends on the previous one, so the prefetcher and out-of-order execution cannot hide latency. Plot ns per access against size and look for the steps at L1, L2 and L3.
  3. Compare. Print measured vs reported (CacheInfo) side by side. On the hybrid laptop, run it pinned to a P-core and to an E-core with taskset -c 0 / taskset -c 7. The steps should move, because the E-cores have a different L1/L2 and no L3. This is a strong result to show in the interview.
// Sattolo: one big cycle, so the chase visits every slot
int[] next = new int[n];
for (int i = 0; i < n; i++) next[i] = i;
Random r = new Random(42);
for (int i = n - 1; i > 0; i--) { int j = r.nextInt(i); int t = next[i]; next[i] = next[j]; next[j] = t; }

int p = 0;
long t0 = System.nanoTime();
for (long k = 0; k < steps; k++) p = next[p];      // each load depends on the last
double nsPerAccess = (System.nanoTime() - t0) / (double) steps;
sink += p;                                         // use p, or the JIT may delete the loop

Java pitfalls to plan for: JIT warm-up (run each size once untimed first), garbage collection (allocate before timing), and the JIT deleting loops whose result is never used. Repeat each point 5 times and keep the median. These pitfalls are good interview material in their own right.

Extension 2: Load and parallelism secondary · , buddy

  • CPU-bound task: count primes up to N, split into equal ranges, one per thread. Each thread keeps its own counter, so there is no shared state or locking.
  • Run on 1, 2, 4, 8, 16 threads. Speedup S(n) = T(1) / T(n), timed with System.nanoTime().
  • While it runs, a sampler thread prints per-core load bars every 0.5 s. This reuses CpuSampler from the core, and you can watch the cores fill up.
  • Amdahl: S(n) = 1 / ((1 − p) + p/n). Estimate the serial fraction from our measurements with the Karp–Flatt metric e = (1/S − 1/n) / (1 − 1/n), then print measured vs predicted.
  • Discussion points: the speedup flattens past 8 threads (8 cores, no SMT). P- and E-cores run at different speeds, so equal-sized chunks finish unevenly. Splitting into many small chunks fixes that, which shows load balancing. On alderaan, VM steal time shows up in /proc/stat.

§10Interview preparation

Every person must be able to answer every question below without notes. Practise in the two mock interviews, and always answer about someone else's area. Tick your name under a question once you can answer it out loud without looking.

What do PCI bus, device and function numbers identify?

The device's address. Bus (8 bits, 0–255) is which PCI bus segment, device (5 bits, 0–31) is the slot on that bus, and function (3 bits, 0–7) is one of several independent functions inside one physical device. For example, 00:14.0 and 00:14.3 are two functions of one chip on Fionn's laptop. The leading 0000 is the PCI domain. In the sysfs folder name these are written in hex.

What is a vendor ID and why do we need a lookup file?

A 16-bit number assigned by PCI-SIG (or USB-IF for USB) to each manufacturer. The hardware only reports numbers, because that is cheap and fixed in silicon. Names live in community-maintained databases (pci.ids, usb.ids), so they can be updated without touching the hardware or the kernel. That is also why some new devices aren't in the file yet.

How did you calculate CPU load from two readings?

/proc/stat gives cumulative ticks since boot per core, split by state. One reading only gives an average since boot. Two readings 1 s apart give the ticks spent in that second. Load = Δbusy / (Δbusy + Δidle). We count iowait as idle and steal as busy, and we can say why.

Why is "used" memory total − available, not total − free?

Linux uses spare RAM as page cache. "Free" leaves out cache, which the kernel can drop at once if a program needs the memory, so total − free would make the machine look nearly full. MemAvailable is the kernel's estimate of what programs can really get.

What is a class code, and what does 0x060400 mean?

24 bits: base class (06 = Bridge), sub class (04 = PCI bridge), programming interface (00). idLookup.className looks up base+sub.

Why does lsusb show "Linux Foundation root hub"?

Each USB host controller (an xHCI PCI device) is shown to the USB stack as a virtual root hub. That keeps the device tree uniform, and Linux reports the hub with its own vendor ID 1d6b.

What did the cache explorer measure, and why use pointer chasing?

Latency per access against working-set size. Each address depends on the previous load, so the CPU cannot run ahead or prefetch. Latency jumps when the working set no longer fits a cache level. Have the actual numbers from our run ready, and the comparison with /sys/.../cache.

Why doesn't the speedup reach n? What does Amdahl say?

Serial parts (thread start-up, combining results), unequal core speeds (P vs E), shared caches and memory bandwidth, the OS and other processes. Amdahl caps the speedup at 1/(1−p) however many cores there are. Quote our measured serial fraction.

Design choices we should be ready to defend

Why we wrapped the index-based starter API in objects. Why we snapshot /proc/stat in one read. Comparable vs Comparator. Why TreeMap (sorted keys) for summaries. Why no build tool or external libraries. How the program copes with missing files.

How does this relate to lectures?

Buses and I/O devices (PCI/USB enumeration), the memory hierarchy (caches, lines, locality), CPU performance (load, parallelism, Amdahl's law), number representation (hex IDs, bit fields in the class code and BDF address), and the OS as the interface to hardware (/proc, /sys).

§11Java, C or C#?

Stay in Java for everything submitted. The brief says the team writes a Java program, the starter is Java, and alderaan is the reference machine. C# needs the .NET runtime, which alderaan probably doesn't have, and it gains us nothing.

One optional idea for later, only if everything else is finished: a ~40-line C version of the pointer-chase loop (C syntax is close to Java for this). Running both shows what the JVM adds (bounds checks, JIT warm-up) against raw C. It is a good critical-thinking point, but strictly a bonus. Leave it out if nobody wants to explain it.
